# Codex Responses 服务 一键迁移部署文档

本包可将 Codex Responses API 代理服务完整迁移到其他机器。镜像内含已编译好的
Codex CLI、app-server、Responses 代理及全部运行时依赖。**不包含任何登录凭证、
API 令牌或历史数据**——在新机器上只需完成一次 Codex 设备码登录即可使用。

## 本版：2026-09-18 后台管理版

镜像：`codex-migration:2026-09-18-admin-ui-bundle1`，Linux amd64。
默认启用管理后台和请求队列；初始并发为 2，页面可调范围为 1–32。

登录服务后打开 `http://127.0.0.1:18876/admin/accounts`，使用
`./migrate.sh token` 获取的 Worker Token 登录。

- 页面支持上传 auth.json、生成 ChatGPT 登录链接并粘贴回调、删除账号和选择当前账号。
- 添加账号只保存配置，点击“设为当前账号”才会更新服务端 Codex 认证。
- 切换账号要求运行中、排队、结果未知的请求全部清空；服务端监听并热加载认证文件。
  接口目前等待 2 秒，尚未对真实双账号切换完成端到端验证。
- 修改并发会即时更新服务端调度器并持久保存，无需重启。
- 页面每 5 秒刷新。账号与 Token 保存在 Docker 数据卷，不随镜像更新丢失。
- 环境变量（端口、代理、并发可选容量等）修改后需运行 `./migrate.sh start` 重建容器。

包内附 `SHA256SUMS`，导入镜像前脚本会核对文件完整性。可手动执行
`sha256sum -c SHA256SUMS`（macOS 使用 `shasum -a 256 -c SHA256SUMS`）。
新机器仍需完成首次设备码登录；部署包不携带源机器账号或令牌。
升级已有部署时保留原 `.env` 和 Docker 数据卷，将 `.env` 中的
`CODEX_WORKER_QUEUE` 设为 `1`，再执行 `./migrate.sh start`。默认项目名
仍为 `codex-migration`，会复用原数据卷。

## 3. 快速开始（三步）

```sh
tar -xzf codex-migration-2026-09-18-admin-ui-linux-amd64.tar.gz
cd codex-migration
./migrate.sh
```

脚本会自动：导入镜像 → 发起设备码登录 → 启动服务并等待健康检查。

登录时会显示：

```text
1. Open this link in your browser and sign in to your account
   https://auth.openai.com/codex/device
2. Enter this one-time code (expires in 15 minutes)
   XXXX-XXXXXX
```

在任意设备浏览器中打开该链接、登录你的 ChatGPT 账号并输入一次性代码即可。
登录成功后脚本自动继续启动服务。**登录态保存在本机 Docker 数据卷中，与
其他机器的登录互不影响。**

## 4. 获取 API Token 并调用

```sh
./migrate.sh token        # 查看 64 位十六进制 Bearer token（首次启动自动生成）
```

服务默认仅绑定本机回环地址：

- Base URL：`http://127.0.0.1:18876/v1`
- 鉴权：`Authorization: Bearer <token>`
- 健康检查：`GET http://127.0.0.1:18876/healthz`（无需鉴权）

### 调用示例

查看模型列表：

```sh
curl -s http://127.0.0.1:18876/v1/models \
  -H "Authorization: Bearer $TOKEN"
```

发起推理（Responses API，流式）：

```sh
curl -N http://127.0.0.1:18876/v1/responses \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.6-terra",
    "instructions": "You are a helpful assistant.",
    "input": [{"type": "message", "role": "user",
               "content": [{"type": "input_text", "text": "你好"}]}],
    "tool_choice": "auto",
    "parallel_tool_calls": false,
    "store": false,
    "stream": true,
    "include": []
  }'
```

> **重要——模型可用性**：`/v1/models` 返回的是模型目录，**不代表你的账号都能
> 调用**。请使用你的账号实际可用的模型（例如账号默认模型）。如果调用返回 502
> 且日志中出现 `model_not_found`，说明该模型对你的账号不可用，请更换模型名。
> 同时建议请求体使用完整的 Responses API 字段结构（如上例），过简的请求体可
> 能被上游拒绝。

## 5. 从其他机器访问服务

默认仅监听 `127.0.0.1`，外部机器无法直接访问。推荐两种方式：

**方式一（推荐）：SSH 端口转发**，无需改动服务配置：

```sh
# 在你的本地电脑执行
ssh -N -L 18876:127.0.0.1:18876 ubuntu@<服务器IP>
# 之后本地访问 http://127.0.0.1:18876/v1 即等同于访问服务器上的服务
```

**方式二：修改绑定地址**（不推荐公网使用，HTTP 明文传输）：

```sh
cp .env.example .env
# 修改 .env：BIND_ADDRESS=0.0.0.0
./migrate.sh restart
```

如必须暴露公网，请在服务前加 TLS 反向代理或使用 VPN，切勿在不可信网络中
明文传输 token 与对话内容。

### 5.1 本机 Sub2API 连接服务器上的 Codex

开发测试时可以使用 SSH 隧道，不需要修改服务器的 `BIND_ADDRESS`，也不会把
Codex API 暴露到公网。在本机执行：

```sh
ssh -N -L 18876:127.0.0.1:18876 <服务器用户>@<服务器IP>
```

保持该 SSH 窗口运行。此时本机的 `127.0.0.1:18876` 会转发到服务器上的
Codex 服务；先确认隧道和服务可用：

```sh
TOKEN="$(ssh <服务器用户>@<服务器IP> 'cd ~/codex-migration && ./migrate.sh token')"
curl -fsS http://127.0.0.1:18876/healthz
curl -fsS http://127.0.0.1:18876/v1/models \
  -H "Authorization: Bearer $TOKEN"
```

在本机 Sub2API 中新增一个 OpenAI-compatible 账号，Base URL 填写
`http://127.0.0.1:18876/v1`，API key 填写上面的 token。若 Sub2API 自身运行
在 Docker 容器内，容器中的 `127.0.0.1` 指向容器自身，应改用
`http://host.docker.internal:18876/v1`，并在 Linux 的 compose 配置中加入：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

然后从 Sub2API 发起一次最小 Responses 请求，确认服务器 Codex 返回结果：

```sh
curl -N http://127.0.0.1:18876/v1/responses \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"model":"<服务器账号可用模型>","input":"ping","stream":true}'
```

Sub2API 应将该账号标记为 OpenAI Responses 兼容渠道，并保留响应中的
`usage` 字段用于费用统计。隧道关闭后，账号健康检查会失败，重新建立 SSH
隧道即可恢复测试。

## 6. 国内服务器（无法直连 OpenAI）的代理配置

国内机器直连 `auth.openai.com` 会得到 403、`chatgpt.com` 会超时。必须为容器
配置**出站代理**：

```sh
cp .env.example .env
```

编辑 `.env`：

```sh
OUTBOUND_PROXY=http://<代理地址>:<端口>
```

注意事项：

- 代理必须是**容器内可达**的地址。服务器本机回环 `127.0.0.1:7890` 在容器内
  指向容器自身，不可用。
- 代理运行在 Docker 宿主机上时，使用 `http://host.docker.internal:<端口>`
  （compose 已配置 host-gateway 映射），并确保代理监听 `0.0.0.0` 或 Docker
  网桥地址（如 `172.17.0.1`），仅监听 `127.0.0.1` 时容器无法连上。
- 代理需支持 CONNECT（HTTPS 代理），登录与模型请求都走它。
- 修改后执行 `./migrate.sh restart` 生效。

验证代理可用：

```sh
curl -x http://<代理地址>:<端口> https://auth.openai.com/.well-known/openid-configuration
# 返回 200 即可用
```

### 方案 B（已在本项目验证）：在服务器自建 mihomo 代理

将本地 Clash 订阅迁移为服务器上的 mihomo 系统服务，服务完全自给自足：

1. 准备文件：`mihomo` Linux amd64 内核（GitHub MetaCubeX/mihomo Releases，
   与本地 Clash Verge 内核同版本即可）、生效的 Clash 配置 `config.yaml`、
   `Country.mmdb` / `geoip.dat` / `geosite.dat`。
2. 修改配置两处（其余保持订阅原样）：

```yaml
allow-lan: true
bind-address: "172.17.0.1"   # 只监听 Docker 网桥：容器可达、公网不可达
```

3. 安装为 systemd 服务：

```sh
sudo mkdir -p /opt/mihomo
sudo cp mihomo config.yaml Country.mmdb geoip.dat geosite.dat /opt/mihomo/
sudo chmod +x /opt/mihomo/mihomo
sudo tee /etc/systemd/system/mihomo.service >/dev/null <<'EOF'
[Unit]
Description=Mihomo (Clash Meta) proxy service
After=network-online.target
Wants=network-online.target
[Service]
Type=simple
LimitNOFILE=65535
ExecStart=/opt/mihomo/mihomo -d /opt/mihomo
Restart=on-failure
RestartSec=5
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable --now mihomo
```

4. 选择可用节点：`url-test` 自动选择可能选中出口被 Cloudflare 拒绝的节点
   （表现为访问 auth.openai.com 得到 403）。通过 REST API 手动切换并验证：

```sh
SOCK=/tmp/verge/verge-mihomo.sock   # external-controller-unix 路径，见配置
SECRET=set-your-secret              # 配置中的 secret
# 切换主组到指定节点（节点名需 URL 编码，PUT body 中用原名）
curl -s --unix-socket $SOCK -H "Authorization: Bearer $SECRET" -X PUT \
  -d '{"name": "节点名"}' "http://localhost/proxies/<组名URL编码>"
# 验证：200 = 可用；403 = 出口被拒，换节点
curl -x http://172.17.0.1:7897 https://auth.openai.com/.well-known/openid-configuration -o /dev/null -w '%{http_code}\n'
```

   手动选择会持久化到 `/opt/mihomo/cache.db`（配置含 `store-selected: true`），
   重启后保持。
5. `.env` 中保持 `OUTBOUND_PROXY=http://host.docker.internal:7897`（compose 已
   将该域名映射到 172.17.0.1），重启服务即可。

> 注意：mihomo 启动时若端口被占用（例如残留的 SSH 反向隧道 `ssh -R
> 172.17.0.1:7897:...`），绑定会失败且不会自动重试，`journalctl -u mihomo`
> 中可见 `bind: address already in use`。先释放端口再 `systemctl restart mihomo`。

## 7. 日常运维

```sh
./migrate.sh              # 首次部署（等同 start）
./migrate.sh start        # 启动（未登录会先要求登录）
./migrate.sh login        # 重新登录/切换账号
./migrate.sh status       # 查看容器状态
./migrate.sh logs         # 查看最近日志（Ctrl+C 退出）
./migrate.sh restart      # 重启
./migrate.sh stop         # 停止
./migrate.sh token        # 查看 API token
```

开启详细日志（排查问题时）：

```sh
echo "RUST_LOG=debug" >> .env
./migrate.sh restart
# 排查完删除该行并重启，避免日志过大
```

## 8. 数据持久化与安全

- 登录凭证、API token、会话数据全部存放在 Docker 数据卷
  `codex-migration_codex-data` 中，重启/升级镜像均保留。
- **不要删除该数据卷**，除非有意清除登录态：`docker volume rm
  codex-migration_codex-data`。
- 迁移到新机器时不要拷贝数据卷，新机器重新登录即可。
- token 泄露时的处理：`docker volume rm codex-migration_codex-data` 后重新
  `./migrate.sh start` 登录，会生成新 token。

## 9. 故障排查

| 现象 | 原因与处理 |
|------|-----------|
| `./migrate.sh` 提示 permission denied (docker.sock) | 当前用户不在 docker 组：`sudo usermod -aG docker $USER` 后重新登录 shell |
| 登录报 `device code request failed with status 403` | 机器无法直连 OpenAI，按第 6 节配置 `OUTBOUND_PROXY` 后重试 `./migrate.sh login` |
| 容器启动失败，日志见 `Login required` | 未登录，执行 `./migrate.sh login` |
| 服务 unhealthy / healthz 不通 | `./migrate.sh logs` 查看启动错误；确认磁盘未满 |
| 调用返回 401 | 请求头 Bearer token 与 `./migrate.sh token` 输出不一致 |
| 调用返回 502 | 查看日志中的上游状态：`model_not_found` = 账号无该模型权限，换模型；连接超时 = 出站代理失效，检查第 6 节 |
| `/v1/models` 正常但推理 502 | 同上，模型目录 ≠ 账号可调用，更换为账号实际可用的模型 |
| 登录成功但推理 401/403 | 登录态过期，`./migrate.sh login` 重新登录 |
| 想彻底重来 | `./migrate.sh stop && docker compose -p codex-migration down -v`（**会清除登录态**），再 `./migrate.sh` |

## 10. 服务架构

```text
客户端 ──HTTP(Bearer)──▶ Nginx :8080（鉴权/健康检查）
                            │ 转发
                            ▼
                  codex-responses-api-proxy :8787
                            │ Unix socket (JSON-RPC)
                            ▼
                     codex-app-server
                            │ HTTPS（走 OUTBOUND_PROXY）
                            ▼
                 ChatGPT 后端 /backend-api/codex
```

- 三个进程由 tini 托管，任一进程退出容器自动退出并由 Docker 重启。
- 容器健康检查探测 `healthz`，与上游可用性无关（`./migrate.sh status` 显示
  healthy 不保证模型可调用）。
